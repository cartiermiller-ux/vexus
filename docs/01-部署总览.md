## 一、这个包里有什么

包根目录（以下简称 `PROJECT`）：

| 目录 | 内容 | 实际用途 |
|---|---|---|
| `源代码/` | admin、api、data 三个 Java Web 工程 + comm/model/dapp 公共源码，`target/classes` 已预编译、`target/dependency` 有 155 个依赖 jar | **源码版后端**（推荐部署路线） |
| `web3_project/admin_u/` | 完整的管理后台 Web 应用（WEB-INF/classes + lib + JSP + 静态资源） | 另一套较新的预编译后台（Dubbo） |
| `web3_project/data_u/` | 完整的行情/WebSocket 数据服务 Web 应用 | 另一套较新的预编译数据服务（Dubbo） |
| `前端wap+pc编译后/zcx/` | 已编译的 PC 站（根目录）+ WAP 站（`wap/` 子目录） | 前台网页静态站 |
| `数据库/dkewl.sql` | 131MB MySQL dump（库名 `jiaoyipan`，129 张表） | 初始化数据库 |
| `截图/` | 前台页面效果图 | 仅参考 |

**重要：包内其实存在两套后端构建产物，二者不能混用。**

| 对比项 | 源码版（`源代码/`） | 预编译 web3 版（`web3_project/`） |
|---|---|---|
| 管理后台 | 需自行组装 WAR（用现成编译产物） | `admin_u` 直接可用 |
| 前台 API | 需自行组装 WAR（用现成编译产物） | **缺失**（包内没有 api webapp） |
| 数据/WebSocket | 需自行组装 WAR | `data_u` 直接可用 |
| 持久层 | Spring JDBC（JdbcTemplate + 注解映射） | Hibernate（hbm.xml） |
| 服务间通信 | 自研 RMI（同 Tomcat 内，端口 20001+） | Dubbo + ZooKeeper |
| 源码完整度 | **完整**（含全部 api 控制器） | 无源码，仅二进制 |
| 数据库 | 配置里写的是 `dapp2`，需改成本包提供的 `jiaoyipan` | 与 `dkewl.sql` 完全对应 |
| 结论 | **推荐：可完整复现、可二开** | 仅作备选/研究，单独无法组成完整站点 |

> 判断依据：`源代码/` 里包含 48 个 API 控制器（`project/web/api/*Controller.java`），
> 覆盖前台 JS 实际请求的 34 个 `/api/xxx.action` 前缀（assets、banner、c2c*、contract*、
> exchange*、finance*、futuresOrder、googleauth、hobi、idcode、item、kyc、loan、localuser、
> miner*、news、otcOnlinechat、rechargeBlockchain、syspara、user、wallet 等）；
> 持久层源码中没有 Hibernate SessionFactory，服务类直接用 `JdbcTemplate`；
> 因此源码版是**功能闭环**的一套，只是需要用包内预编译产物重新组装成 3 个 WAR。

## 二、推荐架构（源码版，三应用 + 静态站）

```
                    ┌──────────────────────────── 浏览器 ────────────────────────────┐
                    │   PC 站 https://your-domain.com/                                │
                    │   WAP 站 https://your-domain.com/wap/                           │
                    │   后台   https://your-domain.com/admin/                          │
                    └───────────────┬───────────────────────────┬─────────────────────┘
                                    │ HTTPS                     │ WSS
                              ┌─────▼─────┐               ┌─────▼──────┐
                              │   Nginx   │               │   Nginx    │
                              │ 静态+反代  │               │ WS 升级    │
                              └──┬──┬──┬──┘               └─────┬──────┘
             /api/  /admin/       │  │  │    /images/ /symbol/   │ /data/
                    ┌────────────▼──┼──▼─────────┐              │
                    │   Tomcat 9（同一实例）       │              │
                    │  ┌─────────┐ ┌─────────┐  │              │
                    │  │  admin  │ │  web    │  │              │
                    │  │ /admin  │ │ /web    │  │              │
                    │  └────┬────┘ └────┬────┘  │              │
                    │  ┌────▼───────────▼────┐  │              │
                    │  │        data         │◄─┼──────────────┘
                    │  │ /data（WebSocket）  │  │
                    │  └────┬────────┬───────┘  │
                    └───────┼────────┼──────────┘
                            │        │
                  ┌─────────▼──┐  ┌──▼─────────┐
                  │  MySQL 5.7 │  │  Redis 6/7 │
                  │  jiaoyipan │  │  127.0.0.1 │
                  └────────────┘  └────────────┘
```

关键点：

1. **admin / web(api) / data 必须部署在同一个 Tomcat、且 context path 都不能为空**。
   源码版通过 Tomcat 内部类枚举同容器 Web 应用，分配 RMI 端口给三个应用互相调用
   （只走 127.0.0.1，不需要对外开放）。
   **原始源码的端口分配依赖 Tomcat children 的 HashMap 顺序，实测第 3 个应用会
   `ObjID already in use` 启动失败；本交付 WAR 已内置 RMI 端口修复补丁**
   （确定性哈希端口 + 动态 context 表，见 `docs/02` 第 11 节）。
   自己从原始源码 Maven 重建时必须覆盖该补丁类，否则不要上线。
2. context 固定为 **`/admin`、`/web`（api 的 WAR 改名为 web）、`/data`**：
   api 控制器 `@RequestMapping` 写死了 `/api/xxx!yyy.action`，因此 api 不能放 `/api`
   （会变成 `/api/api/...`），也不能放 ROOT（旧 RMI 会 NPE），必须放 `/web` 并由 Nginx 做前缀映射。
3. **三个 context 必须按 `admin → web → data` 顺序启动**：data 的 `InitHandle` 启动时
   要通过 RMI 调 `/web` 里 api 的 `C2cTranslateService`。用 Tomcat 按 webapps 目录自动部署时
   顺序是 `admin→data→web`，data 会报 `RMI-Client: Not Implemented Remote Interface` 启动失败。
   解决：Tomcat `server.xml` 关闭自动部署，用 3 个显式 `<Context>` 固定顺序（本机实测通过）。
4. 源码版**不需要 ZooKeeper**。ZooKeeper/Dubbo 是 `web3_project` 那套预编译版才需要的。
5. 前台接口一律是相对路径 `/api/xxx!yyy.action`，Nginx 映射：`/api/ → http://127.0.0.1:8080/web/api/`。
6. 前台 WebSocket 在编译产物里**写死**为 `wss://kelubit.id/data/websocket`，
   必须替换成自己的域名（`deploy/frontend/patch-frontend.*` 脚本会处理）。
7. 上传图片默认落在 `images.dir`，对应 URL 前缀由 `http.server.host` 决定；
   Nginx 需要把 `/images/` 指到该目录。

### 端口/路径约定（本方案统一使用）

| 端口 | 用途 | 是否对外开放 |
|---|---|---|
| 80 / 443 | Nginx（HTTP/HTTPS、WSS） | 是 |
| 8080 | Tomcat HTTP（仅本机） | 否（只允许 127.0.0.1） |
| 20001-20800 / 20999 | 源码版 RMI（同机 Tomcat 内部使用，补丁后按 contextPath 哈希分配） | 否 |
| 3306 | MySQL | 否（只允许 127.0.0.1） |
| 6379 | Redis | 否（只允许 127.0.0.1） |
| 22 | SSH | 建议限制来源 IP |

### 目录规划（本方案统一使用）

| 路径 | 内容 |
|---|---|
| `/www/wwwroot/vexus/site` | 前端 PC 站（`zcx` 内容） |
| `/www/wwwroot/vexus/site/wap` | 前端 WAP 站 |
| `/www/wwwroot/vexus/images` | 后台上传图片（与 `images.dir` 一致） |
| `/www/wwwroot/vexus/logs/{admin,api,data}` | 后端日志（logback.xml 要改路径） |
| `/opt/tomcat9` | Tomcat 安装目录（也可用宝塔的 Tomcat） |
| `/opt/tomcat9/webapps/{admin,web,data}` | 三个应用（api.war 改名 web.war） |
| `/opt/vexus/config-backup` | 修改前配置备份 |

## 三、部署前置条件

- 服务器：Linux（Ubuntu 22.04 / Debian 12 最省事；CentOS 7 已停止维护，不建议）
- 配置：最低 2C4G / 40GB 磁盘；建议 4C8G / 80GB+（三个 JVM 应用 + MySQL + Redis）
- 域名：已备案（如在中国大陆）并解析到服务器
- 软件：JDK 8（Temurin）、Tomcat 9、MySQL 5.7（或 8.0）、Redis 6/7、Nginx、Certbot
- **不要**直接使用 root 跑 Tomcat；建议 `www` 或 `tomcat` 用户
- 源码/构建产物在本机准备好后上传，或在服务器上用脚本原地组装（`deploy/build/build-war.sh`）

> 本部署包在本机（Windows，无 JDK/Tomcat/MySQL）只做了**静态校验**，没有真实启动验证。
> 首次上线前必须在测试环境按本文完整走一遍；验证清单见 `部署教程.md` 第 9 章。

## 四、部署顺序（总清单）

1. 服务器初始化：时区、swap/内核参数、防火墙、创建 `www` 用户、目录。
2. 安装 JDK 8 + Tomcat 9 + MySQL + Redis + Nginx。
   **MySQL 必须先设 `lower_case_table_names=1`**（MySQL 8 要在 initialize 前设置，见 `部署教程.md` 2.3）。
3. 导入 `dkewl.sql` 到 `jiaoyipan` 库（`deploy/sql/import-db.sh`）。
   **源码版还要跑 `deploy/sql/patch-old-source-schema.sql`**（缺 1 表 9 列，否则 Unknown column）。
4. **上线前安全清理**：先按 `部署教程.md` 10.1 建自己的超管，再跑 `deploy/sql/security-cleanup.sql`
   （删隐藏 root、清万能 2FA/外部通道/私钥行/测试号）。
5. 生成数据库密码密文（`deploy/tools/`），修改后端配置（DB/Redis/域名/图片/日志）。
6. 部署 3 个 WAR 到 Tomcat `webapps/{admin,web,data}`（用本交付 `deploy/war/`，内含 RMI 补丁与后门清理）。
   **必须先解压成目录**，并在 server.xml 用显式 `<Context>` 固定启动顺序 admin→web→data。
7. 配置 Tomcat（server.xml、JVM 参数、systemd + RemoteIpValve），先启动一次看日志。
8. 部署前端静态文件（用打过补丁的 `deploy/frontend/zcx`）。
9. 配置 Nginx（静态 + `/api/`→`/web/api/` + `/data/` WebSocket + `/admin/` + `/images/`），签 HTTPS 证书。
10. 初始化后台：用自己的超管登录，改密码、开 Google 验证、配置站点参数。
11. 全链路验收：首页、行情 WS、注册登录、充值/提现、后台审批。
12. 安全加固：按 `docs/05-安全加固与账号.md` 逐项过一遍。
13. 备份与监控：数据库定时备份、日志轮转、磁盘/进程监控。

## 六、先看这里：几条重要提醒

1. **安全（最高优先级）**：这套源码是二次转售的，安全审计确认存在：
   隐藏超管 `SROOT/root`（卖家持密码哈希+万能 2FA 密钥）、未授权后门接口 `character/get|put`、
   前端 C2 `anedhaude.xyz`、钱包地址远程托管 `rpc_node_url`、通讯录外发 `contacts_url`、
   外部 SFTP 整库外传、库中遗留可解密私钥、大量明文凭据。
   **上线前必须按 `部署教程.md` 0.1 节 + `docs/05` 完成清理与轮换，不要直接收真金。**
2. **合规**：运营虚拟货币交易所涉及牌照、反洗钱、外汇与刑事法律风险，请先做法律评估，
   建议只在隔离测试环境学习/验证。
3. **版本**：本方案按「源码版（源代码目录）」组织，因为它是唯一功能闭环的一套
   （web3 预编译版缺 api webapp，不能单独组成完整站点）。若你想用 web3 的较新功能，
   需要自行补齐 api，见 `docs/02` 备选路线。
4. **RMI 补丁**：本交付 `deploy/war` 已内置 RMI 端口修复补丁（否则同一 Tomcat 第 3 个应用
   启动报 `ObjID already in use`）；如果自己从原始源码重建，必须按 `docs/02` 第 11 节覆盖补丁类。
5. **数据库大小写**：Linux 上 MySQL 必须 `lower_case_table_names=1`，否则表名大小写不匹配。见 `部署教程.md` 2.3。
6. **源码版 schema 差异**：`dkewl.sql` 是较新版本导出的，源码版缺 1 表 9 列，必须先跑
   `deploy/sql/patch-old-source-schema.sql`，再跑安全清理 SQL。
7. **已实测**（2026-11-14，Windows 隔离环境）：按本方案部署后三应用同 Tomcat 启动成功，
   `/admin/login.jsp` 200、`/web/api/item!list.action` 返回 JSON、`/data/websocket/1/btc_usdt` 101；
   详见 `部署教程.md` 9.4。生产 Linux/Nginx/HTTPS 仍需按教程复测。
