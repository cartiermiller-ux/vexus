## 2. MySQL 部署与数据导入

### 2.1 版本选择

| 选项 | 建议 |
| --- | --- |
| **MySQL 5.7.x** | ✅ 首选：dump 就是 5.7.34 导出的，`int(11)`/`utf8`/`sql_mode` 天然一致 |
| MySQL 8.0.x | ✅ 可用（Connector/J 8.0.28 已兼容），注意：① 保持库 `utf8` 不要 utf8mb4；② `lower_case_table_names` 只能在 initialize 前设置 |
| MariaDB 10.x | ⚠️ 未验证，`ONLY_FULL_GROUP_BY` 等行为差异可能导致部分统计 SQL 报错 |

**🔥 致命细节：`lower_case_table_names=1`**

- `dkewl.sql` 里表名全是**小写**（`t_wallet`、`sct_user`），而代码里 SQL 全是**大写**（`T_WALLET`、`SCT_USER`，旧源码 297 处、hbm 里也是大写）；
- Linux 上 MySQL 默认 `lower_case_table_names=0`（区分大小写），会直接报
  `Table 'jiaoyipan.T_WALLET' doesn't exist`，**整个站起不来**；
- Windows 版 MySQL 默认就是 1，所以 Windows 部署不会踩这个坑。

```ini
# my.cnf / my.ini 的 [mysqld] 段
lower_case_table_names = 1
```

- MySQL **5.7**：可写入配置文件后重启生效（建议在导入前就设置好；已有库改这个参数后要确认表名无大小写冲突）。
- MySQL **8.0**：该参数**只能在 `mysqld --initialize` 之前**写入配置，装好后再改无法启动。
- 验证：`SHOW VARIABLES LIKE 'lower_case_table_names';` 应为 `1`。

### 2.2 安装（3 种常见环境）

```bash
# CentOS 7 / 宝塔等
yum install -y mysql57-server mysql57  # 或 yum install -y mysql-community-server
systemctl enable --now mysqld
mysql_secure_installation

# Ubuntu/Debian（MySQL 5.7 需先加官方 apt 源；8.0 直接 apt 安装即可）
apt-get install -y mysql-server

# Windows：mysql-5.7.x-winx64.zip 解压 →
#   my.ini 里配 basedir/datadir/lower_case_table_names=1/字符集 →
#   mysqld --initialize-insecure --console →
#   mysqld --install MySQL57 && net start MySQL57
```

推荐 `my.cnf`（`[mysqld]`）关键项：

```ini
[mysqld]
character-set-server = utf8
collation-server = utf8_general_ci
lower_case_table_names = 1
max_allowed_packet = 256M
wait_timeout = 600
interactive_timeout = 600
net_read_timeout = 600
net_write_timeout = 600
innodb_buffer_pool_size = 1G          # 物理内存的 50%~70%
innodb_log_file_size = 256M
innodb_flush_log_at_trx_commit = 2    # 导入期放宽；正式跑改成 1
default-time-zone = '+08:00'          # 与业务/服务器时区一致（可选）
sql_mode = STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION

[client]
default-character-set = utf8
```

### 2.3 建库、建低权限账号

```sql
-- 建库（与 dump 内 SET NAMES utf8 / DEFAULT CHARSET=utf8 对齐）
CREATE DATABASE IF NOT EXISTS `jiaoyipan`
  DEFAULT CHARACTER SET utf8 COLLATE utf8_general_ci;

-- 业务账号：只给本库权限，禁止 GRANT/FILE/SUPER（备份功能如需 mysqldump 再单独授权）
CREATE USER 'vexus'@'127.0.0.1' IDENTIFIED BY '换成你自己的强密码';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, INDEX, REFERENCES
  ON `jiaoyipan`.* TO 'vexus'@'127.0.0.1';
FLUSH PRIVILEGES;

-- 可选：只读账号给报表/排查用
CREATE USER 'vexus_ro'@'127.0.0.1' IDENTIFIED BY '另一个强密码';
GRANT SELECT ON `jiaoyipan`.* TO 'vexus_ro'@'127.0.0.1';
```

> 用 `vexus` 而不是 `root` 之后，**必须**用 `deploy/tools` 把新密码加密成密文再写进配置（见 4.5）。

### 2.4 导入（脚本 or 手工）

**方式 A：一键脚本（推荐）**

```bash
cd deploy/sql
DB_USER=root DB_PASS='root密码' ./import-db.sh        # 导入 + 校验
# 可选：--dry-run 先看命令；--verify-only 只校验；
#       --backup 备份；--restore <gz> --force 回滚
```

脚本会自动检查：mysql 客户端、连接性、`max_allowed_packet`、dump 文件大小（131,302,296 字节）、
Druid 需要的字符集，并在导入后校验表数量与关键表行数。

**方式 B：手工命令**

```bash
# 1) 建库（同上）
# 2) 导入（131MB，普通 SSD 约 3~8 分钟；机械盘/低配云主机可能 10~20 分钟）
time mysql -uroot -p --default-character-set=utf8 --max-allowed-packet=256M \
     jiaoyipan < "/path/数据库/dkewl.sql"
# 3) 看是否有报错：正常应无输出，退出码 0
```

**导入注意**

- `--default-character-set=utf8` **不能省**，否则中文（注释、CMS、币种名）会乱码，且已写入的数据只能重导修复；
- 不要用 `utf8mb4` 建库再导（dump 内是 `utf8`）；
- 导入期间不要同时跑 data 端定时任务/后台，避免锁等待；
- 磁盘预留：数据 + 索引 + binlog 约 **500MB~1GB**；
- 官方 `dkewl.sql` 是**只含表结构和数据**的 dump；无 trigger/存储过程/外键。

### 2.6 失败处理与回滚

| 现象 | 处理 |
| --- | --- |
| `MySQL server has gone away` / `Got a packet bigger than max_allowed_packet` | 调大 `max_allowed_packet=256M`、`net_read_timeout=600`，`DROP DATABASE` 后重导 |
| 中文乱码 | 导入命令漏了 `--default-character-set=utf8`；只能 `DROP DATABASE` 重导 |
| `Table 'jiaoyipan.T_WALLET' doesn't exist`（运行期） | `lower_case_table_names` 不是 1 |
| 导入到一半中断 | `DROP DATABASE IF EXISTS jiaoyipan;` 重建后重导（dump 自带 `DROP TABLE IF EXISTS`，直接重跑一般也行） |
| 想回滚 | 导入前备份：`./import-db.sh --backup`；回滚：`./import-db.sh --restore x.sql.gz --force` |

### 2.7 数据巡检：这份 dump 有「孤儿数据」（重要）

本次实测发现以下**数据不一致**（不是导入问题，是 dump 本身）：

| 表 | 行数 | 问题 |
| --- | --- | --- |
| `t_user` | 783 | 其中 **772 行** 的 `PARTY_ID` 在 `pat_party` 里**不存在**（`pat_party` 只有 12 行） |
| `sct_user_role` | 14 | 其中 **8 行** 的 `USER_UUID` 在 `sct_user` 里不存在（`sct_user` 只有 6 行） |
| `pat_party` / `t_wallet` / `t_userdata` / `t_wallet_log` | 12 / 12 / 10 / 15 | 互相对得上，干净 |

影响：前台用户列表/统计可能出现「有 user 无资料」的空壳行；后台不会崩，但数据看着脏。
建议正式上线前清理（**先备份**，在测试库验证）：

```sql
-- 备份（可选）
CREATE TABLE bak_t_user_orphan AS
SELECT u.* FROM t_user u LEFT JOIN pat_party p ON p.UUID=u.PARTY_ID WHERE p.UUID IS NULL;

-- 删除孤儿 t_user / sct_user_role（确认无误再执行）
DELETE u FROM t_user u LEFT JOIN pat_party p ON p.UUID=u.PARTY_ID WHERE p.UUID IS NULL;
DELETE ur FROM sct_user_role ur LEFT JOIN sct_user su ON su.UUID=ur.USER_UUID WHERE su.UUID IS NULL;

-- 校验
SELECT COUNT(*) FROM t_user;        -- 期望 11（与 pat_party 对应的部分）
SELECT COUNT(*) FROM sct_user_role; -- 期望 6
```

> 也可以反过来「保留 t_user 783 行、补 pat_party」——但缺少资料字段，不如清理干净用后台/前台重新注册测试用户。

## 3. Redis 与 ZooKeeper

| 组件 | 用途 | 部署建议 |
| --- | --- | --- |
| **Redis** | 行情缓存、session/token、客服消息、任务锁 | 只监听 `127.0.0.1`，`requirepass 强密码`；本包 Jedis 2.0.0 老版本，不读 URL 里的密码，靠内网/本机隔离 |
| **ZooKeeper** | Dubbo 注册中心（admin/api/data/dapp 互调） | 单机 `127.0.0.1:2181` 即可；多机换成 ZK 集群地址；`data` 端要单独 `dubbo.application.port.root` 防止端口冲突 |

Redis 最小配置（`redis.conf`）：

```conf
bind 127.0.0.1
protected-mode yes
port 6379
requirepass 换成强密码
maxmemory 1gb
maxmemory-policy allkeys-lru
appendonly yes
```

### 4.4 加载机制与「改了不生效」的坑

1. **`classes/config.properties`（根）才是 Spring 加载的那份**：`applicationContext.xml` 里写的是
   `location="classpath:config.properties"`；`config/config.properties` 只是**副本/历史遗留**（部分老代码或手工工具会读）。
   → 两份都改最稳（脚本/工具里我按「root 优先」标注）。
2. **Redis 真正生效的是 `config/redis.properties`**：`project/redis/interal/Redis.java` 里是
   `PropertiesUtilRedis.getProperty("redis.address").split(";")`；根 `config.properties` 里的
   `redis.address` 在当前版本**没有代码读取**（保留仅兼容）→ 改 Redis 一定要改 `config/redis.properties`。
3. **`images.dir` 出现两次**（根 config.properties 和 config/system.properties）：上传组件与图片 URL 生成各读一份，**两处必须一致**。
4. **jdbc.password 必须是密文**：`LocalDruidDataSource.setPassword()` 会先做 3DES 解密再交给 Druid；
   填明文会导致「密码错误/连接失败」（解密出乱码）。生成方法见 4.5。
5. **`hibernate.hbm2ddl.auto` 无效**：web3 的 `applicationContext.xml` 里该项被注释、旧源码没有 SessionFactory，
   改它不会自动建表/补列（所以缺列必须手动补，见 `deploy/sql/schema-compat-report.md`）。
6. **改完必须重启 Tomcat**：数据源、Redis 连接、Dubbo 注册都在启动时初始化；`system.properties` 类是静态加载，热改无效。
7. **Tomcat 侧建议**（`setenv.sh` / `catalina.bat`）：
   ```text
   JAVA_OPTS="-Xms2g -Xmx4g -XX:+UseG1GC -Dfile.encoding=UTF-8 -Duser.timezone=Asia/Shanghai"
   ```

### 5.3 密码哈希规则（已从源码 + 数据实证）

- Spring 容器：`<bean id="passwordEncoder" class="org.springframework.security.providers.encoding.Md5PasswordEncoder"/>`
  （Spring Security **2.0.8**，`applicationContext-security.xml`）
- 调用：`SecUserServiceImpl.saveUser/updatePassword` → `passwordEncoder.encodePassword(明文, username)`
  （`LoginController.login` 用同一规则校验：`passwordEncoder.encodePassword(password, user.getUsername())`）
- **规则（已用 dump 数据反证）**：

```text
PASSWORD = MD5( 明文 + "{" + USERNAME + "}" )      # 小写 32 位 hex；salt 就是用户名，带花括号
```

验证样例（可直接复算）：

| 用户 | 明文 | 计算 | dump 中哈希 |
| --- | --- | --- | --- |
| test123 | `123456` | `md5("123456{test123}")` | `c4267fb55a40cfc272c74d5f1cf08154` ✅ |
| githajuliani1@gmail.com | `123123` | `md5("123123{githajuliani1@gmail.com}")` | `e25ac59bebe57348f57eb41bb6bcf403` ✅（逐字节一致） |
| root（**SAFEWORD 资金密码**，不是登录密码） | `123123` | `md5("123123{root}")` | `8b14492705d5f7eb0e5a454eae29ead1` ✅（逐字节一致） |

> 该规则同时适用于 `PASSWORD`（登录密码）和 `SAFEWORD`（资金密码）：
> `SecUserServiceImpl.updateSafeword()` 同样调用 `passwordEncoder.encodePassword(明文, username)`。
> 安全文档 `docs/05-安全加固与账号.md` §5 用库中账号（teyung/123456）独立复验，结论一致。

> 注意：`MessageDigestPasswordEncoder` 内部用平台默认字符集 `getBytes()`；密码含中文时，
> 请让 Tomcat 的 `file.encoding`/JVM 默认编码与计算工具保持一致（一般密码只用 ASCII，无此问题）。

### 5.4 默认管理员结论（root）

| 项 | 结论 |

| 默认账号 | **`root`**（UUID=`SROOT`，角色 `SECURITY_ROLE_ROOT`，`ENABLED='y'`）—— **同时是卖家预留的隐藏超管，上线前必须删号重建（见 5.8）** |

**三种可登录方案（按推荐顺序）**

**方案 A（最省事，推荐）：用 2FA 密钥直接绑 App**
1. 手机装 Google Authenticator / Microsoft Authenticator / 1Password 等 TOTP App；
2. 「手动输入密钥」= `62PUGDLBZVHJZPVC`（类型 TOTP，6 位，30 秒）；
3. 用它 + 重置后的密码登录。密钥泄露风险：登录后到后台「谷歌验证器管理」重新绑定新密钥
   （`AdminGoogleAuthController`，页面 `google_auth_admin.jsp`）。

**方案 B：重置 root 密码（不改 2FA）**

```sql
-- 新密码设为 Admin@123456 时（哈希已算好，可直接执行）
UPDATE jiaoyipan.sct_user
   SET PASSWORD = 'd702c1b98af8327ec50aa267e48ba6be'
 WHERE USERNAME = 'root';

-- 其他密码自己算：PASSWORD = md5(明文 + "{root}") 的小写 hex
--   Python:  python3 -c "import hashlib;print(hashlib.md5(('新密码'+'{root}').encode()).hexdigest())"
--   PowerShell: [BitConverter]::ToString([Security.Cryptography.MD5]::Create().ComputeHash(
--               [Text.Encoding]::UTF8.GetBytes('新密码{root}'))).Replace('-','').ToLower()
--   MySQL 8:  SELECT LOWER(MD5(CONCAT('新密码','{root}')));
```

登录后立刻到后台「修改密码」页面再改一次（页面：`password_change.jsp`）。

**方案 C：临时关闭谷歌验证码（仅内网/调试用，别在生产长期开）**

```sql
UPDATE jiaoyipan.t_syspara SET SVALUE='false' WHERE CODE='open_google_auth_code';
UPDATE jiaoyipan.sct_user SET GOOGLE_AUTH_BIND='N' WHERE USERNAME='root';
-- 登录页仍要求填 googleAuthCode，随便填 6 位（如 000000）即可跳过校验
```

## 7. 生产安全建议

> 🚨 **先做安全清理再谈加固**：本包存在隐藏超管 root、万能 2FA 主密钥、4 条外发通道（钱包地址远程托管、
> 通讯录外发、整库 SFTP 外传、第三方短链）、遗留可解密私钥、前端 C2 后门。完整审计见
> `docs/05-安全加固与账号.md`；数据库层清理执行 `deploy/sql/security-cleanup.sql`（说明见 5.8）。
> **只改配置不清后门 = 没清。**

1. **数据库**
   - 只监听内网/本机：`bind-address = 127.0.0.1`（或内网网卡），**绝不 3306 对公网**；
   - 独立低权限账号（`vexus` 只授 `jiaoyipan` 的 DML/DDL，不给 `SUPER/FILE/GRANT`）；
   - root 强密码 + 禁止 root 远程登录：`DELETE FROM mysql.user WHERE User='root' AND Host<>'localhost';`
   - 定期备份（`./import-db.sh --backup` 或 mysqldump + 异地存储），验证可恢复；
   - 打开慢查询日志，定期 `OPTIMIZE TABLE` 大表（`t_kline`/`t_realtime`）或做分区。
2. **Redis**
   - 只监听 `127.0.0.1` + `requirepass` 强密码 + `protected-mode yes`；不要公网开放 6379；
   - 关闭危险命令或改名（`rename-command FLUSHALL ""`）。
3. **配置文件**
   - `jdbc.password` 用 3DES 密文，但**KEY 写死在源码里**（`Roj6#@08SDF87323FG00%jjsd`）→ 密文不等于安全，
     核心还是 DB/Redis 网络隔离 + 权限最小化；
   - `web3_project`、`源代码`、`deploy` 目录不要放进 web 根目录，避免被下载；
   - 配置目录权限 `chmod 600`，属主为 tomcat 运行用户；
   - `t_syspara.backup_server_param`、`t_auto_monitor_address_config.PRIVATE_KEY`（私钥明文！）属于高危数据，限制后台账号权限并定期审计。
4. **后台**
   - 强制 Google 验证码（`open_google_auth_code=true`，已默认开启）；**清空卖家的 `super_google_auth_secret*` 并设置你自己的**；
   - **删除卖家预留的 `root`/`SROOT` 账号**（不是改密码，是删号重建，见 5.8 / `security-cleanup.sql` B 段）；

## 8. 常见故障排查

| 现象（catalina.out / 页面） | 原因 | 处理 |
| --- | --- | --- |
| `Access denied for user 'vexus'@'127.0.0.1'` | 账号密码/授权主机不对 | `SELECT user,host FROM mysql.user;` 补 `'vexus'@'127.0.0.1'`；确认 jdbc.password 是正确密文 |
| `Table 'jiaoyipan.T_WALLET' doesn't exist` | `lower_case_table_names=0` | 设为 1 并重启 MySQL（见 2.1） |
| `Unknown column 'xxx' in 'field list'` | 旧源码版缺列 | 执行 `deploy/sql/patch-old-source-schema.sql` |
| 启动到数据源就停 / `decrypt` 相关异常 | jdbc.password 填了明文 | 用 `deploy/tools` 生成密文 |
| 图片不显示 / 上传失败 | `images.dir` 路径不存在/无权限，或 `http.server.host` 域名错 | 建目录并 `chown tomcat`；两处 `images.dir` 一致 |
| `redis.address 不能为空!` | `config/redis.properties` 缺失或没配 | 补 `redis.address=127.0.0.1:6379` |
| 页面 404（后台所有链接） | Tomcat context 与 `admin_url` 不一致 | 让 war 目录名与 `admin_url` 末段一致（如 `/schw`） |
| 登录提示「谷歌验证码错误」 | 6 位码失效/密钥不对 | 用 `62PUGDLBZVHJZPVC` 重新绑定 App；或按 5.4 方案 B/C |
| 登录提示「未找到用户或用户无权限」 | 该账号角色是 MEMBER/GUEST | 给 `SECURITY_ROLE_ROOT/ADMIN` 等角色（见 5.5） |
| Dubbo 报 `No provider available` | ZK 没起/data 端没起 | 先起 ZooKeeper，再起 data，最后 admin |
| 中文乱码 | 导入/客户端字符集不统一 | 重导时加 `--default-character-set=utf8`；Tomcat 加 `-Dfile.encoding=UTF-8` |
| `Communications link failure` | MySQL 没起/端口不对/防火墙 | `telnet 127.0.0.1 3306`；查 `bind-address` |
