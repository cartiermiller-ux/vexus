## 一、部署形态与三个关键结论

### 1.1 形态

源码版后端是 **3 个 Spring MVC Web 应用**，必须部署在**同一个 Tomcat 9** 下：

| WAR | 部署为 | context path | 作用 |
|---|---|---|---|
| `admin.war` | `webapps/admin` | `/admin` | 管理后台（JSP + Spring MVC，`/admin/normal/*!*.action`） |
| `api.war` | **`webapps/web`** | **`/web`** | 前台 JSON 接口（控制器写死 `/api/*!*.action`，见下方结论 2） |
| `data.war` | `webapps/data` | `/data` | 行情/WebSocket 推送 + 定时任务（K 线、归集、监控等） |

```text
                         浏览器 / APP
                              │ HTTPS(443) / WSS
                       ┌──────▼──────┐
                       │   Nginx     │  静态站 + 反代 + WS 升级
                       └──┬────┬─────┘
          /admin/         │    │        /api/  /public/  /wap/api/  /wap/public/  /data/
                          │    │           （重写前缀）
                       ┌──▼────▼──────────────────────────────────────┐
                       │            Tomcat 9（同一 JVM）                │
                       │  /admin          /web              /data      │
                       │  admin.war       api.war           data.war   │
                       │     └────── RMI 127.0.0.1:20001+ ──────┘       │
                       └───────────────┬───────────────┬────────────────┘
                                       │               │
                                 ┌─────▼─────┐   ┌─────▼─────┐
                                 │  MySQL    │   │  Redis    │
                                 │ jiaoyipan │   │ 127.0.0.1 │
                                 └───────────┘   └───────────┘
```

### 1.2 三个必须记住的结论

1. **三个应用必须放同一个 Tomcat、context 都不能为空**。旧版服务间调用是自研 RMI：
   `kernel.web.RmiProxyFactoryBean` 静态块通过 Tomcat 内部类枚举同容器所有 context，
   并在各自端口创建 RMI registry（细节见第十一节）。
   **源码版不需要 ZooKeeper**；ZooKeeper/Dubbo 是 `web3_project` 新版才需要的。
   ⚠️ 原始源码的 `RmiProxyFactoryBean` 按 Tomcat children 的 HashMap 顺序分配 20001+ 端口，
   **三个应用放同一 Tomcat 时第 3 个必因端口重复启动失败**（`ExportException: ObjID already in use`）；
   本交付的 WAR 已用补丁类覆盖（确定性端口 + 动态 context 表，见 11.4），
   **若你自己从源码重新构建，必须把这个补丁类覆盖回去**。
2. **api.war 必须部署在非空 context `/web`，不能是 `/api`、也不能是 ROOT**：
   - api 控制器的 `@RequestMapping` 写死为 `/api/xxx.action`（例如
     `/api/assets!getAll.action`，编译产物中共 217 条 `/api/*.action` 字符串）。
   - 若放 context `/api` → 实际 URL 变成 `/api/api/xxx.action`，前台请求 `/api/xxx.action` 全部 404。
   - 若放 ROOT（context 为空）→ `RmiProxyFactoryBean` 过滤空 context 后查不到自己，
     `rmiPortMap.get("")` 返回 null → 静态块抛异常，**启动即崩**。
   - 正确做法：放 `/web`，Tomcat 本机 URL 是 `/web/api/xxx.action`，
     Nginx 把外部 `/api/` 重写到 `/web/api/`（见第十三节）。**本机验证接口时必须用 `/web/api/...`。**
3. **上线前必须执行安全清理**（详见第十六节）：
   - WAR 已删除卖家后门类、脱敏旧凭据，但 `project/monitor/noderpc/**` 因 Spring 强依赖**保留**，
     必须执行 `deploy/sql/security-cleanup.sql` 把 `t_syspara.rpc_node_url`、`contacts_url` 等清空；
   - 改用自己账号：删除隐藏 root 超级账号、轮换 2FA 主密钥（见 `docs/05`、`docs/03`）；
   - 不按第十六节做完，**不允许对外提供真实资金服务**。

## 二、服务器要求

| 项 | 最低 | 推荐 |
|---|---|---|
| CPU | 2 核 | 4 核+（管理员 + API + 数据任务 + 行情推送都在跑） |
| 内存 | 4 GB | 8 GB+（Tomcat 单 JVM 跑 3 个应用 + MySQL + Redis） |
| 磁盘 | 40 GB SSD | 80 GB+（131MB SQL 解压后约 1GB+，另有日志/上传/备份） |
| 系统 | Ubuntu 22.04 / Debian 12 | 同上；CentOS 7 已停止维护不推荐 |
| 带宽 | 5 Mbps | 10 Mbps+（行情/WS 长连接 + 图片流量） |
| 时区 | Asia/Shanghai | 与 `-Duser.timezone=Asia/Shanghai` 一致，`timedatectl` 校准 |
| 网络 | 可访问外网（行情源） | 需允许出站访问行情/区块链节点接口；若源站不可达，data 服务行情推送无数据 |

**端口规划**（本方案统一使用）：

| 端口 | 用途 | 是否对外开放 |
|---|---|---|
| 80 / 443 | Nginx（HTTP/HTTPS、WSS） | ✅ 是 |
| 8080 | Tomcat HTTP（建议只绑 127.0.0.1，由 Nginx 反代） | ❌ 否 |
| 20001-20800 | 源码版自研 RMI（同机 Tomcat 内部用；**本交付 WAR 已打确定性端口补丁**，见第十一节） | ❌ 否（防火墙禁止） |
| 20999 | RMI 补丁给 ROOT context（空 context）的兜底端口，正常部署用不到 | ❌ 否 |
| 3306 | MySQL | ❌ 否（只允许 127.0.0.1） |
| 6379 | Redis | ❌ 否（只允许 127.0.0.1） |
| 22 | SSH | 建议限制来源 IP |

## 五、部署三个 WAR（关键：api 放 context=/web）

### 5.1 上传

在本地打包机上把 `deploy/war/` 三个文件上传到服务器，例如 `/root/vexus-war/`：

```bash
scp deploy/war/admin.war deploy/war/api.war deploy/war/data.war root@服务器IP:/root/vexus-war/
```

> 也可以把 `deploy/build/{build-war.ps1,build-war.sh}` 拷到服务器后用 `build-war.sh` 现场构建（见第十八节）。

### 5.2 解压到 webapps（**先解压、改配置、再启动**）

先解压再改配置，避免 Tomcat 第一次启动就因 DB 密码占位符连不上库（也避免 WAR/目录并存时被覆盖）：

```bash
cd /opt/tomcat9/webapps
sudo rm -rf admin web data

# admin → /admin
sudo unzip -q /root/vexus-war/admin.war -d admin

# api   → /web（注意目录名：context=/web，不是 /api！）
sudo unzip -q /root/vexus-war/api.war -d web

# data  → /data
sudo unzip -q /root/vexus-war/data.war -d data

sudo chown -R tomcat:tomcat /opt/tomcat9/webapps/{admin,web,data}
```

> 为什么 api 要放 `/web`：见第一节结论 2。**部署目录名 = context path**，
> `webapps/web` 的 context 就是 `/web`（Tomcat 默认规则）。改目录名即可改 context，不需要额外 context.xml。
> 如果直接用 WAR 自动部署（把 war 放 webapps），必须把 `api.war` 重命名为 `web.war`，
> 否则 context 会是 `/api`、接口全部 404。
>
> ✅ 本交付的 3 个 WAR **已内置 RMI 端口修复补丁**（`kernel/web/RmiProxyFactoryBean.class` 为补丁版，
> 见第十一节 11.3），解压即用，无需再手工替换；若自己从源码重建则必须覆盖补丁类（11.6）。

校验解压结果：

```bash
ls /opt/tomcat9/webapps/admin/WEB-INF/web.xml
ls /opt/tomcat9/webapps/web/WEB-INF/web.xml
ls /opt/tomcat9/webapps/data/WEB-INF/web.xml
ls /opt/tomcat9/webapps/admin/login.jsp
test -d /opt/tomcat9/webapps/admin/WEB-INF/classes && echo OK
```

## 六、修改配置（DB/Redis/域名/日志/图片）

### 6.1 修改前先备份

```bash
sudo cp -a /opt/tomcat9/webapps/admin/WEB-INF/classes/config.properties /opt/vexus/config-backup/admin-config.properties.bak
sudo cp -a /opt/tomcat9/webapps/admin/WEB-INF/classes/config /opt/vexus/config-backup/admin-config.bak
# web、data 同理
```

### 6.2 用模板 + 工具替换配置（推荐）

> 配置分为两层：**根 `classes/config.properties`**（jdbc/redis/dubbo/images）和
> **`classes/config/*.properties`**（system/redis/db/email/sms/...）。逐项映射见
> `deploy/config/README.md`，这里只说三端都要改的关键项。

**1) 生成 DB 密码 3DES 密文**（`LocalDruidDataSource` 会对 `jdbc.password` 解密，**明文必失败**）：

```bash
python3 deploy/tools/db_password.py encrypt '你的database密码'
# 输出形如 xxxxxx%2Bxxxx%3D%3D，粘到 jdbc.password = 后面
```

（Windows：`powershell -File deploy\tools\DbPassword.ps1 -Password '你的数据库密码'`，见 `deploy/tools/README.md`）

**2) 三个应用的 `classes/config.properties`（根）**：

| 键 | 值 | 说明 |
|---|---|---|
| `jdbc.url` | `jdbc:mysql://127.0.0.1:3306/jiaoyipan?useUnicode=true&characterEncoding=utf-8&useSSL=false&allowPublicKeyRetrieval=true` | 库名按 `docs/03` 导入结果；与 SQL 一致 |
| `jdbc.username` | `vexus` | 按 `docs/03` 创建的数据库用户 |
| `jdbc.password` | `<上一步生成的 3DES 密文>` | **密文**，不是明文 |
| `images.dir` | `/www/wwwroot/vexus/images/` | 上传目录，三端一致 |
| `redis.address` | `127.0.0.1:6379` | 旧版根配置里的 redis 无代码读取，真正生效在 `config/redis.properties`，但两处保持一致最稳 |
| `email.*` | 自己的 SMTP（不用可留空） | WAR 里已清空卖家账号 |

**3) 三个应用的 `classes/config/system.properties`**：

| 键 | 值 |
|---|---|
| `admin_url` | `https://your-domain.com/admin`（后台登录成功后的跳转根） |
| `web_url` | `https://your-domain.com/wap/`（前台 WAP 站地址，用于拼 showimg 等图片 URL） |
| `http.server.host` | `https://your-domain.com/images/`（图片对外前缀） |
| `images.dir` | `/www/wwwroot/vexus/images/`（与根配置一致、且目录可写） |
| `encryption.key`（仅 api） | 32 位随机 hex；**必须与前端补丁约定一致**，否则 API 登录验签失败 |

**4) 三个应用的 `classes/config/redis.properties`**：

```properties
redis.address=127.0.0.1:6379
redis.address.port=6379
```

**5) 其它配置（按需）**：
- `config/email.properties`：发邮件才填（SMTP）；
- `config/sms253.properties`：发短信才填（实际通道由 `t_syspara.send_code_type` 决定）；
- `config/db.properties`：用后台"数据库备份/还原"功能才需要（`db.password` 同样是 3DES 密文）；
- `config/autoe2due.properties` 的 `chartext`：卖家域名私钥口令，WAR 中已改为 `REPLACE_ME`，
  **建议保持占位**（该功能属卖家链上归集，需按 `docs/05` 决定是否启用）。

## 七、Tomcat `server.xml` 关键配置

编辑 `/opt/tomcat9/conf/server.xml`，**备份原文件**。关键项如下（片段，非完整文件）：

```xml
<Server port="8005" shutdown="SHUTDOWN" address="127.0.0.1">
  <!-- 8005 关闭端口只绑本机；也可设为 -1 彻底关闭（用 systemctl 停服务） -->

  <Service name="Catalina">
    <!-- HTTP Connector：只绑 127.0.0.1，由 Nginx 对外；URIEncoding 必须 UTF-8（中文参数） -->
    <Connector port="8080" protocol="HTTP/1.1"
               address="127.0.0.1"
               connectionTimeout="20000"
               redirectPort="8443"
               URIEncoding="UTF-8"
               useBodyEncodingForURI="false"
               maxThreads="300"
               minSpareThreads="20"
               acceptCount="200"
               maxConnections="8192"
               compression="on"
               compressionMinSize="2048"
               compressableMimeType="text/html,text/xml,text/plain,text/css,text/javascript,application/javascript,application/json" />

    <!-- AJP 不使用：整段注释掉（默认 8009，不要对外） -->
    <!--
    <Connector port="8009" protocol="AJP/1.3" redirectPort="8443" />
    -->

    <Engine name="Catalina" defaultHost="localhost">
      <!-- 【关键】三个应用必须按 admin → web(api) → data 的顺序启动。
           目录自动部署的顺序是 admin→data→web；data 启动时其 InitHandle 需要
           /web 里 api 提供的 C2cTranslateServiceImpl，/web 还没起来就会报
           "RMI-Client: Not Implemented Remote Interface: project.c2c.C2cTranslateService"。
           因此关闭自动部署，用下面 3 个显式 <Context> 固定顺序（本机实测通过）。 -->
      <Host name="localhost" appBase="webapps" unpackWARs="true"
            autoDeploy="false" deployOnStartup="false">
        <!-- 可选：Tomcat 自带 access log -->
        <Valve className="org.apache.catalina.valves.AccessLogValve" directory="logs"
               prefix="localhost_access_log" suffix=".txt"
               pattern="%h %l %u %t &quot;%r&quot; %s %b" />

        <!-- 【重要】配合 Nginx 反代 + admin basePath 补丁：识别 X-Forwarded-* -->
        <Valve className="org.apache.catalina.valves.RemoteIpValve"
               remoteIpHeader="X-Forwarded-For"
               protocolHeader="X-Forwarded-Proto"
               protocolHeaderHttpsValue="https"
               portHeader="X-Forwarded-Port" />

        <!-- 顺序不能改：admin → web(api) → data -->
        <Context docBase="admin" path="/admin" reloadable="false" />
        <Context docBase="web"   path="/web"   reloadable="false" />
        <Context docBase="data"  path="/data"  reloadable="false" />
      </Host>
    </Engine>
  </Service>
</Server>
```

**说明**：

1. `address="127.0.0.1"`：Tomcat 不直接暴露公网，统一走 Nginx。若暂时不用 Nginx、想直接
   `http://IP:8080/admin/login.jsp` 验证，可先去掉 `address` 属性，验证完再加回并开防火墙限制。
2. `URIEncoding="UTF-8"`：旧版大量中文参数/JSP，缺了会乱码。
3. `maxThreads` 与 Nginx 上游连接数匹配；2C4G 起步机可用 200，4C8G 用 300~500。
4. **AJP 必须注释/禁用**（Ghostcat 风险，且本方案不用 AJP）。
5. `RemoteIpValve` 与构建时打的 `basePath.jsp` 补丁是"双保险"：JSP 优先读 `X-Forwarded-*`，
   即使 Valve 没生效也不会生成 `http://域名:8080/...` 的错误地址；但 Nginx 必须传这些头（见第十三节）。
6. **显式 `<Context>` + `autoDeploy="false" deployOnStartup="false"` 是本方案要求**：
   - 三个 WAR 必须先解压成 `webapps/admin`、`webapps/web`、`webapps/data` 目录（见 5.2），
     不要只放 WAR 文件（关闭自动部署后 WAR 不会被自动解压）；
   - 启动顺序固定 admin → web → data，解决 data 启动依赖 /web 的 RMI 服务问题；
   - 若不用显式 Context 而让 Tomcat 自动部署，目录们会按字母序 admin→data→web 启动，
     data 很可能启动失败（实测报 `RMI-Client: Not Implemented Remote Interface`）。
7. 每个应用如需自定义 context 属性，可在 `webapps/<app>/META-INF/context.xml` 加
   `<Context reloadable="false" />`；用了显式 `<Context>` 后以 server.xml 为准。

## 八、JVM 参数 `setenv.sh`

创建 `/opt/tomcat9/bin/setenv.sh`（Windows 本地测试则是 `setenv.bat`），内容示例（**4C8G 机器**）：

```bash
#!/bin/bash
# /opt/tomcat9/bin/setenv.sh  —— Tomcat 启动前自动 source
export JAVA_HOME=/usr/lib/jvm/temurin-8-jdk-amd64
export JRE_HOME="$JAVA_HOME/jre"

export CATALINA_OPTS="
  -server
  -Xms1g -Xmx2g
  -XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m
  -Dfile.encoding=UTF-8
  -Dsun.jnu.encoding=UTF-8
  -Duser.timezone=Asia/Shanghai
  -Djava.awt.headless=true
  -Djava.security.egd=file:/dev/./urandom
  -XX:+HeapDumpOnOutOfMemoryError
  -XX:HeapDumpPath=/www/wwwroot/vexus/logs
  -Dlogback.configurationFile=/opt/vexus/logback-admin.xml
"
```

> - 三个应用在**同一个 JVM** 里，`-Xmx` 是给三个应用共享的：4G 内存机器建议 `-Xms512m -Xmx1536m`；
> 8G 机器建议 `-Xms1g -Xmx2g`（本文示例）；16G 可 `-Xmx4g`。`-Xms` 与 `-Xmx` 设相同可减少抖动。
> - `-Dlogback.configurationFile=...` 只在采用"方案 B 外置日志"时添加，并且要按应用区分：
>   一个 Tomcat 共享 JVM 参数无法给 3 个应用不同值，**所以外置日志方案需放进各应用自己的启动参数
>   （Tomcat 不支持 per-webapp system property）**；更简单的做法是用 6.4 的方案 A 直接改 logback.xml。
> - JDK 8 默认 GC 是 Parallel，够用；如需 G1 加 `-XX:+UseG1GC -XX:MaxGCPauseMillis=200`。
> - `-Duser.timezone=Asia/Shanghai` 必须加，否则 K 线/订单时间会偏 8 小时。

```bash
sudo chmod +x /opt/tomcat9/bin/setenv.sh
sudo chown tomcat:tomcat /opt/tomcat9/bin/setenv.sh
```

## 十一、自研 RMI：端口说明、实测问题与补丁

旧版没有 ZooKeeper/Dubbo，服务之间用**自研 RMI**互调，实现见
`kernel/web/RmiProxyFactoryBean.java` 与 `kernel/rmi/RmiInvocationHandler.java`。

### 11.1 原始实现的机制

1. 每个应用启动时，静态块通过 Tomcat 内部类（`ApplicationContextFacade.getContext()` 反射 +
   `StandardContext.getParent().findChildren()`）枚举**同一 Tomcat 容器内所有 context**；
2. 过滤掉空 context（`getContextPath().trim().isEmpty()`），放进 `LinkedHashMap`；
3. 按 `findChildren()` 的迭代顺序从 **20001** 开始给每个 context 分配端口：第 1 个 20001、第 2 个 20002…
4. 每个应用在**自己分配到的端口**上 `LocateRegistry.createRegistry(port)` 并 `bind("rmi", RmiFacadeImpl)`，
   其他应用按 `rmiPortMap.get(远端contextPath)` 找到端口后 `Naming.lookup("rmi://127.0.0.1:<port>/rmi")` 调用。

### 11.2 原始实现的致命缺陷（local-verify 实测确认，三应用同 Tomcat 必现）

**现象**：admin、api 先启动后，第 3 个 `data` 应用启动失败，`catalina.out` 报：

```text
java.rmi.server.ExportException: internal error: ObjID already in use
    at sun.rmi.transport.ObjectTable.putObject(ObjectTable.java:146)
    at sun.rmi.transport.tcp.TCPEndpoint.exportObject(TCPEndpoint.java:401)
    at java.rmi.server.UnicastServerRef.exportObject(UnicastServerRef.java:189)
    at java.rmi.registry.RegistryImpl.setup(RegistryImpl.java:153)
    at java.rmi.registry.RegistryImpl.<init>(RegistryImpl.java:116)
    at java.rmi.registry.LocateRegistry.createRegistry(LocateRegistry.java:186)
    at kernel.web.RmiProxyFactoryBean.<clinit>(RmiProxyFactoryBean.java:77)
...
SEVERE: Context [/data] startup failed due to previous errors
```

**根因**（两个）：

1. **端口分配依赖 HashMap 迭代顺序**：`findChildren()` 返回的 children 顺序在 Tomcat 实现里并不可靠
   （HashMap 迭代顺序与启动先后相关）。三个应用各自在自己的类加载器里静态初始化时，
   同一时刻枚举到的 children 集合不同/顺序不同，导致 admin 与 data 都算出 20002，
   `LocateRegistry.createRegistry(20002)` 第二次执行时抛 `ObjID already in use`。
2. **context 表只快照一次**：`servletContextMaps` 在类初始化时快照，先启动的应用看不到后启动的 context，
   跨应用 RMI 调用会 `NOT_FOUND_CONTEXT` / `NOT_IMPLEMENTED_INTERFACE`。

### 11.3 本交付 WAR 已应用的修复（构建时强制覆盖）

| 项 | 值 |
|---|---|
| 覆盖目标 | 三个 WAR 的 `WEB-INF/classes/kernel/web/` 下 **4 个 class 文件**（外层 + 3 个内部类） |
| 补丁 class | `deploy/build/patched/kernel/web/RmiProxyFactoryBean.class`（5558B）+ `$1.class`、`$DynamicContextMap.class`、`$DeterministicPortMap.class` |
| 补丁源码 | `deploy/build/patches/kernel/web/RmiProxyFactoryBean.java` |
| 产物来源 | **local-verify 实测编译并通过验证的版本**（三个 WAR 内逐文件 SHA256 与实测产物一致） |
| 补丁逻辑 | ① 端口 = `20001 + \|contextPath.hashCode()\| % 800`，**确定性**，与启动顺序/context 数量无关；② `servletContextMaps` 改为动态视图，每次 `containsKey/get/entrySet` 前重新读取 Tomcat children；③ ROOT（空 context）固定端口 **20999**，不再 NPE |
| 校验方式 | WAR 内 4 个 class 均存在，且 SHA256 与 `deploy/build/patched/kernel/web/` 一致；构建脚本已做强制断言（外层缺失/内部类不全直接失败） |
| WAR 内说明 | `WEB-INF/classes/kernel/web/RMI-PATCH-README.txt` 记录了补丁原因与重建方法 |

因此采用本交付的 WAR 后，三个应用的 RMI 端口由 context path 唯一确定（`/admin`、`/web`、`/data` 各一个
固定值，落在 **20001-20800** 范围内），**不再依赖启动顺序**，第 3 个应用不会端口冲突。

### 11.4 部署约束（补丁后仍需遵守）

| 约束 | 原因/后果 |
|---|---|
| 三个应用必须**同一个 Tomcat 实例** | RMI 靠"同容器 context 枚举"找端口，跨 Tomcat/跨机找不到 |
| context path 必须**非空**（推荐 `/admin`、`/web`、`/data`） | 补丁虽给 ROOT 兜底 20999，但 ROOT 会与前台静态站抢根路径，不推荐 |
| context 名不能随意改 | 有 spring 配置显式引用 `remoteContextPath=/data`；改了会 `NOT_FOUND_CONTEXT /data`，且端口哈希值随之变化 |
| **RMI 端口为确定性哈希，不是连续的 20001/20002/20003** | 排查/防火墙用 **20001-20800** 范围（外加 20999 兜底） |
| 三应用要**同时在线** | 缺一个时，调用它的 bean 会 `NOT_FOUND_CONTEXT` 或连接拒绝（首次调用时暴露） |
| **不能单独热部署/重启一个应用** | 同一 context 的新 classloader 会再次 bind 同端口 → `BindException`；只能整体重启 Tomcat |
| RMI registry **监听 0.0.0.0** | `LocateRegistry.createRegistry` 默认监听所有网卡，必须防火墙/安全组禁止 20001-20800、20999 对外 |
| 依赖 Tomcat 内部类 | 只能跑 **Tomcat 9**（WAR 内不能带 tomcat-catalina 等 jar；本包已排除） |
| 不需要 ZooKeeper | 旧版 `config.properties` 里的 `dubbo.registry.address=127.0.0.1:2181` 是残留配置，无代码使用 |

### 11.5 常见排错

- `ExportException: internal error: ObjID already in use`（第 3 个应用启动失败）→ 用了**未打补丁的
  RmiProxyFactoryBean**（源码原始版/自己 Maven 重建的 WAR）。用本交付的 WAR，或按 11.6 覆盖补丁类。
- `java.rmi.server.ExportException: Port already in use` → 有残留 Tomcat 进程或同一机器部署了第二套；
  `pkill -f catalina` 后整套重启，并确认机器上只跑一套。
- `Not Found Tomcat HTTP/1.1 Port` → `ApplicationUtil.getLocalPort()` 通过 JMX 找 `HTTP/1.1`
  Connector 失败：检查 server.xml Connector 是否 `protocol="HTTP/1.1"`、是否只剩 AJP、是否有多套。
- `NOT_FOUND_CONTEXT /data` / `NOT_IMPLEMENTED_INTERFACE` → 对应应用没起/context 名不对/接口实现类缺失。

### 11.6 如果自己用 Maven 从原始源码重建，必须覆盖补丁类

补丁只存在于**本交付的 WAR** 与 `deploy/build/patched/`。若用 `mvn clean package` 从
`源代码/` 重新构建，编译出的 `kernel/web/RmiProxyFactoryBean.class` 是**原始有缺陷版本**，必须覆盖：

```bash
# 项目根执行（JDK8；源码在 deploy/build/patches/，实测产物在 deploy/build/patched/）
javac -source 8 -target 8 -encoding UTF-8 \
  -cp "源代码/admin/target/classes:源代码/admin/target/dependency/*" \
  -d deploy/build/patched \
  deploy/build/patches/kernel/web/RmiProxyFactoryBean.java
# 然后对每个应用（或对重建出的 WAR 解包后）覆盖全部 4 个 class（外层 + 3 个内部类，缺一不可）：
cp deploy/build/patched/kernel/web/RmiProxyFactoryBean*.class \
   <解包目录>/WEB-INF/classes/kernel/web/
```

> Windows 版构建脚本会**自动**做这一步，且在补丁文件缺失时直接报错退出，避免产出会挂的包。
> 验证方法：WAR 内 class 含 `DeterministicPortMap`/`DynamicContextMap` 标记，或 SHA256 与
> `deploy/build/patched/kernel/web/RmiProxyFactoryBean.class` 一致（见 `deploy/war/MANIFEST.md` 4.2 节）。

**防火墙示例（ufw）**：

```bash
sudo ufw allow 80,443/tcp
sudo ufw deny 8080/tcp
sudo ufw deny 20001:20800/tcp
sudo ufw deny 20999/tcp
sudo ufw reload
```

## 十三、Nginx 反代要点（后端视角）

> 完整 server 配置（静态站、HTTPS、WSS、缓存）见 `docs/04-前端与Nginx.md`，这里只列与后端强相关的转发规则。
> 所有 `proxy_set_header` 里的 `X-Forwarded-*` 都是 **admin basePath 补丁 + RemoteIpValve** 的依赖，**不能省**。

```nginx
# 后台
location /admin/ {
    proxy_pass         http://127.0.0.1:8080/admin/;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
    proxy_set_header   X-Forwarded-Host  $host;
    proxy_set_header   X-Forwarded-Port  $server_port;
    proxy_http_version 1.1;
}

# 前台 API：外部 /api/... → Tomcat /web/api/...
# 注意 proxy_pass 末尾带 /api/：
#   /api/item!list.action → http://127.0.0.1:8080/web/api/item!list.action
location /api/ {
    proxy_pass         http://127.0.0.1:8080/web/api/;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
    proxy_set_header   X-Forwarded-Host  $host;
    proxy_set_header   X-Forwarded-Port  $server_port;
    proxy_http_version 1.1;
}

# 图片上传/展示（api 里 /public/uploadimg、/public/showimg 等）
location /public/ {
    proxy_pass         http://127.0.0.1:8080/web/public/;
}
# WAP 站也可能用 /wap/api/、/wap/public/ 前缀（前端补丁后按实际引用决定）
location /wap/api/ {
    proxy_pass         http://127.0.0.1:8080/web/api/;
}
location /wap/public/ {
    proxy_pass         http://127.0.0.1:8080/web/public/;
}

# 数据服务 WebSocket
location /data/ {
    proxy_pass         http://127.0.0.1:8080/data/;
    proxy_http_version 1.1;
    proxy_set_header   Upgrade           $http_upgrade;
    proxy_set_header   Connection        "upgrade";
    proxy_set_header   Host              $host;
    proxy_set_header   X-Real-IP         $remote_addr;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}

# 上传图片静态目录
location /images/ {
    alias /www/wwwroot/vexus/images/;
    expires 7d;
}
```

## 十四、上传目录与图片

- `images.dir`（根 config.properties 与 config/system.properties 两处）必须指向
  `/www/wwwroot/vexus/images/`，且对运行用户（`tomcat`）可写：

  sudo chown -R tomcat:tomcat /www/wwwroot/vexus/images

## 十五、常见错误排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `/admin/login.jsp` 404 | admin 没解压出来 / webapps 下目录名不对 / Tomcat 没重启 | `ls webapps/admin/login.jsp`；看 catalina.out 是否 `Deployment of web application archive ... has finished` |
| `/api/xxx.action` 404 / 返回空 | api 部署成了 context `/api`（URL 变 `/api/api/...`）或 ROOT 启动失败 | 必须部署为 `webapps/web`，本机验证 `/web/api/...`；Nginx 反代 `/api/` → `/web/api/` |
| `/web/api/xxx.action` 404 | api 应用启动失败 / `WEB-INF/classes` 不完整 / 控制器类被误删 | 看 catalina.out 完整堆栈；确认 `web/WEB-INF/classes/project/web/api/*Controller.class` 存在 |
| 启动报 `ClassNotFoundException: javax.servlet.*` / `jakarta.servlet.*` | 用了 Tomcat 10/11（Jakarta）或 WAR 里误带容器 jar | 换回 **Tomcat 9**；本包 WAR 已排除 servlet-api/tomcat-* jar |
| 启动报 `NoClassDefFoundError: org/apache/poi/assistant/MD5` 且只在开启验签时出现 | 安全清理删了 poi 后门类，而 api `AllRequestFilter` 只有在 `config/system.properties` 的 `version.number` 非空时才走验签分支（默认空） | 保持 `version.number=`（空）即可；若开启验签需二次开发替换 MD5 实现 |
| 启动报 `NoClassDefFoundError: project/monitor/noderpc/...` | 有人手工删了 noderpc 类 | 不要删 noderpc 包（见第十六节）；用本交付的 WAR |
| 启动报 `ClassNotFoundException: kernel.web.SpringWebContextListener` | `WEB-INF/classes` 内容缺失（手工拷贝时漏了 class） | 重新用 `deploy/war/*.war` 完整解压 |
| JSP 500 / `Unable to compile class for JSP` | ①JSP 被改坏（如 basePath 补丁重复变量）②JDK 版本不对 ③`jstl` 缺失 | 看 `/opt/tomcat9/logs/localhost.*.log` 具体行；用交付 WAR 的原始 JSP；确认 lib 里有 `jstl-1.2.jar` |
| 后台 CSS/JS 全挂、跳 `http://域名:8080/...` | 用的是旧 basePath.jsp（没有反代补丁）或 Nginx 没传 X-Forwarded-* | 用本交付 admin.war；Nginx 加 `X-Forwarded-Proto/Host/Port`；server.xml 加 RemoteIpValve |
| `The connection property 'zeroDateTimeBehavior' ...` / `Unknown database 'jiaoyipan'` | DB 未导入/库名不一致/jdbc.url 没改 | 按 `docs/03` 导入；三端 `jdbc.url` 统一 |
| `Access denied for user 'vexus'@'localhost'` | DB 用户/密码不对 | 用 `deploy/tools` 生成 `jdbc.password` 密文；`mysql -uvexus -p` 先本机验证 |
| `Cannot create PoolableConnectionFactory` / Druid 初始化失败 | `jdbc.password` 填了明文（LocalDruidDataSource 会 3DES 解密）或 DB 未启动 | 填密文；`systemctl status mysql` |
| Redis 相关报错 `Could not get a resource from the pool` / `Connection refused` | Redis 没启动/地址错/`config/redis.properties` 没改 | `redis-cli ping`；三端 `config/redis.properties` 改 `127.0.0.1:6379` |
| `Port already in use: 20001` / RMI 异常 | 同一机器跑了第二套 Tomcat，或单独热部署残留 registry | 只保留一套；`systemctl stop` 后 `pkill -f catalina`；整套重启 |
| `NOT_FOUND_CONTEXT /data` | data 没部署/context 名不是 `/data` | 三应用同一 Tomcat；目录名必须 `data` |
| `Not Found Tomcat HTTP/1.1 Port` | JMX 找不到 HTTP/1.1 Connector（protocol 被改/AJP-only/多套） | server.xml Connector 用 `protocol="HTTP/1.1"`；只跑一套 |
| 启动很慢/大量行情报错 | data 连接外部行情源失败（无外网/被墙） | 确保服务器可访问行情源；不影响 Tomcat 启动与后台 |
| `OutOfMemoryError: Java heap space` | JVM 太小 / 定时任务/行情数据量大 | 调大 `-Xmx`（8G 机 2g，16G 机 4g）；看 `jmap`/heapdump |
| 中文乱码（后台/参数） | 缺 UTF-8 配置 | server.xml `URIEncoding="UTF-8"`；JVM `-Dfile.encoding=UTF-8`；jdbc URL `characterEncoding=utf-8`；DB 库/表 utf8mb4 |
| 上传图片 404 | Nginx 未配 `/images/`，或 `images.dir` 与目录不一致 | 看第十四节 |
| 日志目录不存在/无权限 | logback 还是 `/root/logs`，运行用户是 tomcat | 改 `logback.xml` 的 `logPath` 并 `chown` |
| 后台登录后跳回登录/接口 403 | token/域名不一致、`admin_url` 配错、Cookie 域不对 | 统一域名；`admin_url` 配 `https://域名/admin`；清浏览器缓存再试 |
| 访问 `/admin/schw/...` 或 `/admin/root/...` 资源 404 | 旧版 JSP 静态引用在根 `css/js`，`normal/` 是控制器 URL 前缀；`schw/root` 是旧皮肤残留未打包 | 正常，不影响功能；如页面确实引用需二次开发补资源 |
| 访问旧页面出现 404（如 `adminEmailCodeAction`、`adminSymbolsAction` 等） | 旧版 JSP 引用了该编译产物中不存在的 7 组控制器（卖家版本残留） | 已知限制，见第二十节；不影响登录/主流程 |

## 十七、admin JSP 的 basePath Nginx 反代补丁（已内置）

**问题**：旧版 `源代码/admin/src/main/webapp/include/basePath.jsp` 写死：

```jsp
String basePath = request.getScheme()+"://"+request.getServerName()+":"+request.getServerPort()+path+"/";
String base = "http://" + request.getServerName() + ":"+request.getServerPort()+"/";
```

Tomcat 在 Nginx 后面时 `getScheme()=http`、`getServerPort()=8080`，后台所有 CSS/JS/AJAX 会变成
`http://域名:8080/admin/...`（HTTPS 下还会混合内容被浏览器拦截），后台直接不可用。

**已处理**：构建 admin.war 时把 6 个 JSP 里的 basePath/base 计算替换为优先读代理头：

```jsp
<%
String path = request.getContextPath();
String proxyScheme = request.getHeader("X-Forwarded-Proto");
if (proxyScheme == null || proxyScheme.trim().isEmpty()) { proxyScheme = request.getScheme(); }
proxyScheme = proxyScheme.trim();
String proxyHost = request.getHeader("X-Forwarded-Host");
if (proxyHost == null || proxyHost.trim().isEmpty()) { proxyHost = request.getServerName(); }
proxyHost = proxyHost.trim();
String proxyPort = request.getHeader("X-Forwarded-Port");
if (proxyPort == null) { proxyPort = ""; }
proxyPort = proxyPort.trim();
String proxyHostPort = proxyHost;
if (!proxyPort.isEmpty()) {
    if (!"80".equals(proxyPort) && !"443".equals(proxyPort)) { proxyHostPort = proxyHost + ":" + proxyPort; }
} else {
    int proxyServerPort = request.getServerPort();
    if (proxyServerPort != 80 && proxyServerPort != 443) { proxyHostPort = proxyHost + ":" + proxyServerPort; }
}
String basePath = proxyScheme + "://" + proxyHostPort + path + "/";
String base = proxyScheme + "://" + proxyHostPort + "/";
%>
```

涉及文件：`include/basePath.jsp`、`include/email_code.jsp`、`include/google_auth_code.jsp`、
`include/jquery.jsp`、`include/pagetop.jsp`、`simple_loan_order_edit.jsp`（后者把内联
`request.getScheme()+"://"+request.getServerName()` 改为使用 `base`）。补丁幂等，保留 `path/basePath/base`
三个变量，JSP 其它地方引用不受影响。

**部署要求**：
1. Nginx 反代 `/admin/` 时必须带 `X-Forwarded-Proto`、`X-Forwarded-Host`、`X-Forwarded-Port`（第十三节）；
2. Tomcat `server.xml` 的 `<Host>` 里加 `RemoteIpValve`（第七节）作为双保险；
3. 若发现后台仍跳 `http://域名:8080`，说明用的不是本交付 admin.war，或 Nginx 没传头。

## 十八、不打包、直接 exploded 部署（等价步骤）

如果不想在本地打包、希望在服务器上直接部署 exploded 目录，有**两种等价做法**（结果与 WAR 解压一致）：

### 方式 A：服务器上用 `build-war.sh` 现场构建 exploded 目录（推荐，最快）

```bash
# 1) 把整个 PROJECT 包上传到 /root/vexus-src（或只上传 PROJECT/源代码 与 PROJECT/web3_project/admin_u/normal）
#    目录结构需保持：/root/vexus-src/Vexus.../源代码/{admin,api,data,...}
# 2) 构建并保留 exploded 目录（KEEP_WORK=1）
cd /root/vexus-src/VexusXXX/deploy/build
KEEP_WORK=1 bash build-war.sh /root/vexus-src/VexusXXX   # 参数=项目根（含“源代码”的目录）

# 3) 把 exploded 目录移到 webapps（注意 api → web）
cd /opt/tomcat9/webapps
sudo rm -rf admin web data
sudo mv /tmp/vexus-war-build/admin admin
sudo mv /tmp/vexus-war-build/api   web      # 关键：目录名 web
sudo mv /tmp/vexus-war-build/data  data
sudo chown -R tomcat:tomcat admin web data
```

> `build-war.sh` 与 `.ps1` 逻辑等价：同样做安全清理、配置脱敏、admin basePath 补丁、jar 排除。
> 服务器需要 `zip`：`apt install -y zip`（或 `yum install -y zip`）。

### 方式 B：手工从源码目录组装（不执行脚本，等价于脚本做的事）

```bash
SRC=/root/vexus-src/VexusXXX/源代码
WEB=/opt/tomcat9/webapps

for app in admin api data; do
  case "$app" in api) ctx=web ;; *) ctx=$app ;; esac
  dst="$WEB/$ctx"
  sudo rm -rf "$dst"
  sudo mkdir -p "$dst/WEB-INF/classes" "$dst/WEB-INF/lib"

  # 1) webapp 静态资源 + JSP（admin 有；api/data 只有 WEB-INF，无静态资源）
  if [ -d "$SRC/$app/src/main/webapp" ]; then
    (cd "$SRC/$app/src/main/webapp" && sudo find . -type f \
        -not -path './WEB-INF/*' \
        ! -name '.DS_Store' ! -name 'Thumbs.db' ! -name '~$*' ! -name '*.log' \
        | sudo cpio -pdm "$dst")
    sudo cp "$SRC/$app/src/main/webapp/WEB-INF/web.xml" "$dst/WEB-INF/web.xml"
  fi

  # 2) 编译类（注意：复制后必须按第十六节删除后门类、按 6.2 脱敏配置）
  sudo cp -a "$SRC/$app/target/classes/." "$dst/WEB-INF/classes/"

  # 3) 依赖 jar（排除容器提供的 14 个）
  (cd "$SRC/$app/target/dependency" && sudo find . -maxdepth 1 -type f -name '*.jar' \
      ! -name 'tomcat-*' ! -name 'javax.servlet-api-*' ! -name 'javax.websocket-api-*' \
      | while read -r j; do sudo cp "$j" "$dst/WEB-INF/lib/"; done)

  # 4) admin 补 normal 主题 + basePath 反代补丁 + 安全清理 + 配置脱敏 + RMI 补丁覆盖
  if [ "$app" = admin ]; then
    sudo cp -a /root/vexus-src/VexusXXX/web3_project/admin_u/normal "$dst/normal"
    # 建议直接用 build-war.sh 完成补丁/清理/脱敏，避免手工漏项
  fi
  # 5) RMI 端口修复补丁：三个应用都必须覆盖，否则第 3 个应用启动失败（见第十一节）
  sudo mkdir -p "$dst/WEB-INF/classes/kernel/web"
  sudo cp /root/vexus-src/VexusXXX/deploy/build/patched/kernel/web/RmiProxyFactoryBean.class \
          "$dst/WEB-INF/classes/kernel/web/RmiProxyFactoryBean.class"
done
sudo chown -R tomcat:tomcat "$WEB"/{admin,web,data}
```

> 手工方式**极易漏掉**：① 安全清理（删后门类）；② 配置脱敏；③ admin basePath 补丁；
> ④ 排除 14 个容器 jar；⑤ **覆盖 RMI 端口修复补丁类**（否则第 3 个应用启动失败）。
> 因此推荐用方式 A 的脚本，或直接用 `deploy/war` 解压（第五节）。
> 三种方式产出的 exploded 目录结构完全一致，后续配置/启动步骤相同。

## 十九、备选路线：web3_project 预编译版

`PROJECT/web3_project` 下有一套较新的预编译部署包：

| 项 | `admin_u` | `data_u` |
|---|---|---|
| 形态 | 完整 webapp（JSP/静态 + `WEB-INF/{classes,lib,web.xml}`） | 完整 webapp（`WEB-INF`） |
| classes | 1309 个（含 97 个 `*.hbm.xml`） | 1273 个（含 96 个 `*.hbm.xml`） |
| lib | 143 个 jar（约 94.7MB） | 127 个 jar（约 78MB） |
| 持久层 | **Hibernate**（hbm 映射） | **Hibernate** |
| 服务通信 | **Dubbo + ZooKeeper**（`127.0.0.1:2181`） | **Dubbo + ZooKeeper** |
| API 接口层 | **缺失**（包内没有 api webapp） | 不适用 |
| 额外功能 | 跟单（copy-trading）、在线客服等新版页面 | 新版行情服务 |

**结论：这套只能作为"二开/研究"的备选路线，不能直接组成完整站点。**

原因：它缺 api webapp。前台所有数据请求都走 `/api/xxx.action`，没有 api 应用：
- 不能把旧版 api 混搭进来——旧版用自研 RMI、新版用 Dubbo/ZooKeeper，服务调用机制不兼容；
- 也不能"跳过 api"——前台 PC/WAP 站会直接 500/404。

如果确实要走这条路，需要：① 部署 ZooKeeper（`127.0.0.1:2181`）+ 三端 Dubbo 配置；② 自己补齐 api 层
（从旧版 api 源码改造为 Dubbo consumer 或 REST）；③ 配置 Hibernate 数据源与 hbm 映射；
④ 重新做安全审计（新版同样来自卖家，不是可信产物）。工作量和风险都明显高于本文推荐的源码版路线。

部署形态（仅供参考，**未验证**）：

```text
webapps/admin  ← admin_u 内容（context=/admin）
webapps/data   ← data_u 内容（context=/data）
（缺 api，需要自研补齐）
ZooKeeper 127.0.0.1:2181 必须存在
```

不建议把两套混在同一个 Tomcat：旧版 RMI（本交付已改为按 contextPath 确定性哈希分配端口）
与新版 Dubbo 应用共用同一个容器容易引发端口/上下文混乱。

## 二十、已知限制与未验证项

1. **本机（构建机）未真实启动**：没有 JDK/Tomcat/MySQL/Redis，本包只通过"包内容静态校验 + 安全断言"。
   Spring 容器初始化、DB/Redis 连通性、RMI 端口绑定、JSP 编译、WebSocket 握手、上传目录写入，
   均需在测试环境实测；本机由 local-verify 在独立环境实测，结果以其记录为准。
2. **`noderpc` 类保留**（第十六节 16.2）：属兼容性取舍，必须靠 `security-cleanup.sql` + 网络阻断消除可用性；
   WAR 内仍有 9 个 `project/monitor/noderpc/**` class（已知豁免项，见 `deploy/war/MANIFEST.md`）。
3. **配置占位符必须先替换**：`jdbc.password=REPLACE_WITH_3DES_CIPHERTEXT`、
   `encryption.key=REPLACE_WITH_RANDOM_32_HEX`、域名/邮箱等全部为占位；不替换无法正常启动/登录。
4. **7 组旧 JSP 失效按钮**：旧版 JSP 引用了该版本编译产物中不存在的控制器
   （`adminEmailCodeAction`、`adminExchangeLeverAction`、`adminMinerParaAction`、
   `adminRoleAuthorityManageAction`、`adminSymbolsAction`、`adminUserMoneyStatisticsAction`、
   `identifyingCodeAction`），对应页面/按钮 404。属卖家版本残留，不影响登录/主流程。
5. **data 应用没有 index.jsp**：`/data/` 根路径 404 是正常的（服务无页面），WebSocket 与 action 正常即可；
   行情源不可达时只有日志报错，不影响 Tomcat 启动。
6. **RMI 端口为确定性哈希（20001+hash%800，另 20999 为 ROOT 兜底）**，不是连续 20001/20002/20003；
   RMI registry 监听 0.0.0.0，必须防火墙阻断 20001-20800 与 20999（第十一节）。
   **原始源码的 RmiProxyFactoryBean 有端口冲突缺陷，本交付 WAR 已打补丁；若自己 Maven 重建必须覆盖补丁类，
   否则第 3 个应用启动必失败（见 11.2/11.6 与 `deploy/war/MANIFEST.md` 4.2）。**
7. **只能 Tomcat 9 + JDK8**：Tomcat 10（Jakarta）不能部署；JDK 11/17 理论上可跑 Java8 字节码 +
   Spring 5.3，但旧版依赖与 JSP 兼容性未验证，**请用 JDK 8 与 Tomcat 9**。
8. **`version.number` 必须留空**：api 的 `AllRequestFilter` 在 `version.number` 非空时会调用
   已删除的 poi 后门类 `MD5.sign()` 做验签（安全清理后该类不存在）→ 500。保持
   `config/system.properties` 的 `version.number=` 为空即可（默认即为空）。
9. **前端必须用补丁产物**：`wss://kelubit.id`、`anedhaude.xyz` 等卖家域名在前端编译产物里，
   必须使用 `deploy/frontend` 的补丁版本（见 `docs/04`），否则 API/WS 地址与后端 context 对不上。
10. **Hibernate/hbm 不需要**：源码版无 Hibernate SessionFactory，`*.hbm.xml` 不打包（见 MANIFEST）；
    `config.properties` 里的 `hibernate.*` 是残留配置，无代码读取。
